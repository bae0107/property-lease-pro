# 二、项目故事 1：公共组件开发

## 项目关键词

**任务框架 / 网元树组件 / Turbo-CSV / 鉴权切面 / 公共能力沉淀 / 提效**

## 背景

在华为公共开发部，不同业务团队有很多重复能力，例如任务处理、资源树展示、CSV 数据处理、权限校验等。如果每个团队各自实现，容易出现代码重复、质量不一致、维护成本高的问题。

## 我的职责

我主要负责公共组件的设计和开发，把多个业务都需要的能力抽象成统一组件，供业务团队复用。

## 我做了什么

* 设计开发任务框架，统一任务创建、执行、状态流转、异常处理和日志记录。
* 设计网元树组件，支撑复杂层级资源展示和查询。
* 开发 Turbo-CSV 组件，提升大文件数据处理效率。
* 通过鉴权切面，把权限校验逻辑从业务代码中剥离出来，减少重复代码。

## 难点

公共组件最难的是**边界控制**。组件不能写死某个业务逻辑，但又要满足多个业务场景。

## 我的设计思路

公共组件只提供通用机制，例如生命周期、扩展点、策略接口、统一异常和日志规范。具体业务差异通过接口、配置、回调或策略类扩展。

## 结果

这些组件提升了团队开发效率，减少重复实现，也让代码风格和质量更加统一。

## 面试时加分句

> 我理解公共组件不是简单写工具类，而是要把稳定的通用机制和变化的业务逻辑隔离开。

# 三、项目故事 2：服务云化版本切换

## 项目关键词

**云化迁移 / Docker / Kubernetes / 配置外置化 / 健康检查 / 日志 / 回滚 / 版本兼容**

## 背景

原有系统需要从传统部署模式逐步迁移到云原生环境。这个过程不是简单把服务打成镜像，还涉及配置、依赖、日志、资源、监控和发布方式的变化。

## 我的职责

我参与多个服务的云化版本切换，负责应用侧适配、问题定位、版本验证和迁移风险处理。

## 我做了什么

* 梳理服务依赖：数据库、配置文件、三方件、二方件、文件路径、启动参数。
* 配合完成容器化部署适配。
* 处理不同环境下配置差异，推动配置外置化。
* 调整日志输出，适配云环境日志采集。
* 关注服务启动、健康检查、资源占用和性能回归。
* 处理版本兼容问题，保障迁移过程平滑。

## 难点

云化迁移容易暴露传统部署下隐藏的问题，比如本地路径依赖、启动顺序依赖、配置耦合、日志路径固定、资源占用不清楚等。

## 我的设计思路

先梳理依赖，再做应用适配；先保证可部署，再保证可观测、可回滚、可稳定运行。

## 结果

完成多个服务的云化版本切换，支撑系统平滑迁移到云原生架构。

## 面试时加分句

> 我更熟悉的是云上应用开发和迁移适配，包括配置、日志、健康检查、资源限制、性能回归和版本兼容，而不是单纯把服务放进容器。

# 四、项目故事 3：云上数据平台迁移与 IO 性能优化

## 项目关键词

**数据平台 / 公有云到私有云 / 实时接入 / 高并发 IO / 数据读写优化 / 性能提升**

## 背景

在车 BU 数据平台部门，系统需要支撑车辆数据实时接入，并完成从公有云到私有云的架构迁移。迁移过程中，对数据接入性能、读写效率和系统稳定性要求比较高。

## 我的职责

我参与云上数据平台搭建和迁移，负责数据链路优化、性能瓶颈定位和版本适配。

## 我做了什么

* 分析数据接入链路，定位高并发场景下的 IO 瓶颈。
* 优化数据读写流程，减少不必要的阻塞和重复操作。
* 关注批量处理、线程模型、数据库访问和存储访问效率。
* 处理三方件、二方件版本适配和兼容性问题。
* 通过指标对比验证优化效果。

## 难点

高并发 IO 问题不能只看代码，可能出现在应用线程、数据库、磁盘、网络、下游服务或批处理策略上。

## 我的定位方法

我会先看指标，再定位瓶颈：

* 接口耗时
* 吞吐量
* CPU / 内存
* GC 情况
* 线程阻塞
* 数据库慢 SQL
* 磁盘 IO
* 下游依赖耗时

## 结果

优化数据读写流程，解决高并发场景下 IO 瓶颈，系统响应效率有明显提升。

## 面试时加分句

> 性能优化不能靠猜，我一般会先按链路分层定位，再根据指标做针对性优化。

# 五、项目故事 4：线上内存溢出与性能问题定位

## 项目关键词

**OOM / CPU 高 / Full GC / 线程堆积 / dump / jstack / 性能瓶颈 / 稳定性**

## 背景

大型系统运行过程中，会遇到内存溢出、接口变慢、CPU 飙高、线程堆积、数据库慢查询等问题。这类问题通常影响生产稳定性，需要快速定位和修复。

## 我的职责

我长期承担技术攻坚角色，参与过内存溢出、性能瓶颈等高风险问题定位和修复。

## 我怎么排查 OOM

如果是内存溢出，我一般按下面思路处理：

1. 先确认 OOM 类型：堆内存、Metaspace、Direct Memory，还是线程创建失败。
2. 保留现场：日志、GC 日志、heap dump。
3. 分析对象数量、对象大小、引用链和增长趋势。
4. 判断是内存泄漏，还是瞬时大对象。
5. 常见排查点包括无界缓存、大集合、批量查询、线程池队列、未释放引用等。

## 我怎么排查 CPU 高

如果是 CPU 高，我一般这样做：

1. 先确认是哪个 Java 进程。
2. 找到高 CPU 线程。
3. 把线程 ID 转成 16 进制，对应 jstack。
4. 看线程栈中热点方法。
5. 判断是死循环、锁竞争、频繁 GC、序列化、正则、日志过多，还是其他问题。

## 我怎么排查接口慢

我会按链路拆分：

* 网关 / 接口入口
* 应用逻辑
* 线程池
* 数据库
* 缓存
* 下游服务
* 网络和 IO

## 结果

定位并修复多类内存和性能问题，保障系统稳定性。

## 面试时加分句

> 线上问题处理最重要的是先保留现场，再分层定位，不能一上来就凭经验改代码。

* 不要一直强调“18 年经验”，要强调**复杂系统、工程落地、性能优化、稳定性**。
